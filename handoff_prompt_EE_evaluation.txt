## TL;DR: where things actually stand

The investigation moved through several hypotheses (reward bugs, entropy
mechanism, network capacity) before landing on the one that actually
mattered: **this project used to train every model at
EE_TRAIN_ERROR_BOUND=0.5, an error range 10x larger than the reference
paper ever uses.** Retraining at realistic error levels (0.0 and 0.05,
matching the paper's own Fig. 3 training points) produced genuine power
savings (~56% of budget) and a rate-vs-error curve with the paper's
expected shape (higher-error-trained model degrades more gracefully,
crossing over the zero-error-trained model around error~0.045).

Since then, several follow-up investigations all held up and sharpened the
picture further:
- **The full paper-matching three-point set (0.0/0.025/0.05) is now
  trained and evaluated**, not just 0.0/0.05. Clean, monotonic crossovers:
  0.025-trained overtakes 0.0-trained around error~0.035-0.04, and is
  itself overtaken by 0.05-trained further out. See "error=0.025 SAC
  checkpoint" below.
- **Classical baselines (MMSE/MRT/ZF) added for comparison.** At full
  power budget they beat SAC on raw rate, as expected -- but they always
  use 100% of the budget by construction, while SAC only uses ~56%. Once
  MMSE is constrained to the SAME 56 W SAC actually uses, the two are
  statistically tied at zero error (MMSE 3.39 vs SAC 3.36 bps/Hz), and MMSE
  degrades much faster under CSIT error than at full power -- SAC's
  crossover advantage at higher error is even more pronounced against this
  power-matched baseline. See "Classical baseline comparison" below.
- **Channel correlation confirmed as a real, physical driver of variance**
  in this scenario, unrelated to training -- see "Channel correlation
  investigation" below.
- **Beampattern comparison (EE vs. "regular" 100W SAC)**: sometimes EE
  matches the regular checkpoint's spatial strategy exactly, just with a
  sharper/differently-scaled beam; other times EE spatially abandons the
  weakest-channel user to concentrate power on the other two -- genuinely
  realization-dependent, not a fixed rule. See "Beampattern comparison"
  below.

Three fresh Optuna hyperparameter searches are still running (one per
error bound: 0.0, 0.025, 0.05) to find good learning rates before
potentially retraining "final" SAC checkpoints -- see "Optuna searches"

## Channel correlation investigation

Explores whether high correlation between users' channels (a purely
geometric/physical property, independent of any training) is a real
difficulty in this N16K3/100km scenario -- see src/utils/calc_channel_correlation.py
(normalized complex inner product between two users' channel vectors;
|correlation|=1 means spatially indistinguishable, no precoder can help).

**Zero-error, our actual operating point** (channel_correlation_zero_error.py,
10,000-sample MC, wiggle enabled -- our real scenario, not a sweep): User1-User2
mean=0.077 (max 0.993), User1-User3 mean=0.042 (max 0.081, never spikes),
User2-User3 mean=0.076 (max 0.992). Two of three pairs occasionally spike
to near-total correlation; the third never does -- a geometric effect of
whichever user ends up "in the middle" of the +-50km roam range.

**Distance sweep** (channel_correlation_distance_sweep.py, wraps the
pre-existing src/analysis/test_channel_correlation_distance_sweep.py --
needed a headless-safe rewrapper, that file has neither matplotlib.use('Agg')
nor a non-blocking save, would hang forever in a SLURM job; also used a
coarser 40-point grid instead of the original's 200-point grid to keep
runtime reasonable, disable_wiggle=True i.e. pure distance dependence, no
roam): correlation collapses from ~0.999 at 500m to ~0.2 by 20km, then
flattens into a noisy 0.02-0.2 floor for the rest of the range with no
further systematic trend. At our 100km mean operating point: 0.041 --
solidly in the low-noise floor. Together with the zero-error result above,
this shows the mean 100km distance itself is NOT a correlation risk; the
occasional near-1.0 spikes come from the +-50km ROAM occasionally pushing a
pair's effective distance down into the steep sub-20km region, not from
the mean distance choice.

## Satellite hardware parameter cross-check: 3GPP TR 38.821 vs. config.py -- DONE, one real discrepancy found (sat_gain_dBi)

Three reference documents were searched this session for satellite
hardware/power parameters to validate against config.py. **General method
for searching ANY new reference doc for parameters** (reuse this recipe --
don't re-derive it): extract the doc's full text with the appropriate tool,
ALWAYS wrapped in a .slurm + sbatch (never run directly, per the sbatch-only
rule), write the extracted text to `outputs/<name>_extracted_text.txt`, then
`grep -ni` for the parameter keywords (antenna gain, EIRP, PA/HPA efficiency,
circuit power, noise figure, antenna temperature, back-off, altitude/orbit,
etc.) against the .txt file -- grepping/reading a plain-text file afterward
is not compute and doesn't need sbatch, only the extraction step does.
- **.doc (legacy binary Word)**: no antiword/wvWare/libreoffice/pandoc and no
  sudo on this machine (confirmed: libreoffice isn't on conda-forge
  linux-64 either, apt needs a password) -- use `olefile` (pip-installed) to
  open the OLE compound file, read the "WordDocument" stream, decode as
  single-byte **CP1252 (NOT UTF-16** -- UTF-16 produces mojibake since Word
  compresses plain-Latin-text runs to 1 byte/char), then regex out
  printable-character runs. Script: src/energy_efficiency/extract_38821_doc.py
  (+ matching .slurm). Page numbers: the doc's own TOC PAGEREF fields cache
  a page number as a SEPARATE short (1-3 char) text run right after the
  field code -- a naive regex with a length-4+ minimum filters these out
  silently; a second low-threshold (length-1+) pass recovers them. Only
  gives page numbers at clause granularity (TOC entries), not per-table --
  individual tables within a clause aren't separately paginated.
- **.pdf**: `pdftotext -layout <file> <out>.txt` (already installed at
  /usr/bin/pdftotext, no python PDF library available -- checked
  pdfplumber/PyPDF2/fitz, none installed). `-layout` preserves table
  structure reasonably well. Page numbers: pdftotext inserts a `\f`
  (form-feed) between pages -- `text.split('\f')` gives one list entry per
  PDF page, 1-indexed, so `grep`-ing a keyword then checking which split
  chunk it falls in gives an exact page number (more reliable than the .doc
  TOC-cache approach above).

**Result 3: PPA paper -- the one real amplifier-efficiency number found**
(Yan, Ramesh, Gallagher, Ling, Cabric, "Performance, Power, and Area Design
Trade-offs in Millimeter-Wave Transmitter Beamforming Architectures",
arXiv:1807.07201, src/energy_efficiency/Performance_Power_and_Area_Design_
Trade-offs_in_Mi.pdf, 20 pages -- terrestrial mmWave 5G BS array design,
NOT satellite, but the only source found with an actual numeric PA
efficiency derivation). Page 12 (Section IV.D, near Fig. 7): gives a PA
power-consumption model P_PA = P_out / (N * eta_PA) with **eta_PA = 0.185**
(18.5%) adopted, explicitly derived from **0.3 peak PAE, 10dB power
back-off, Doherty PA architecture** (footnote: Doherty PAs hold PAE more
constant across back-off than simpler Class A/AB/B, which is why they
picked it as the reference topology). Fig. 7 (same page) is a survey of
state-of-the-art 28GHz PA measurements across CMOS/SiGe BiCMOS/GaAs/GaN
process technologies (refs [71]-[82]), saturated output power vs. peak PAE.

**pa_efficiency discrepancy, now with three data points**: our config.py
uses 0.60 (60%, from Ha et al. 2023/2024, satellite-specific, "60% for both
antenna/HPA efficiency" per the existing code comment); the PPA paper gives
0.185 (18.5%, terrestrial mmWave, realistic 10dB-backed-off operating
point); the OLD (already-superseded) config value was 0.35 (35%, Auer et
al. 2011, sub-6GHz terrestrial). **60% vs. 18.5% is a >3x gap.** Neither is
obviously "more correct" -- Ha et al. is satellite-domain-matched but the
PPA number is grounded in a concrete back-off/architecture derivation with
real measured PA data behind it, illustrating how sensitive PA efficiency
actually is to operating point (back-off from saturation) and amplifier
architecture. Given `pa_efficiency` directly scales `power_constraint_watt`
into the DC-draw denominator of the whole energy-efficiency reward/metric,
this single assumption is worth a sensitivity check (e.g. re-run the power
savings/rate numbers at eta=0.185 or eta=0.35 alongside the current 0.60,
see how much the headline power-savings percentage moves) if the EE
numbers are ever presented outside this project.

**Result 4 (follow-up, user-prompted): "antenna efficiency" is a DIFFERENT,
separate quantity from pa_efficiency -- and our model doesn't have it at
all.** User asked whether 3GPP's "antenna aperture efficiency" (0.55-0.70,
found in the Link Budget Calculation clause 6.1.3.1, TOC page ~51-52 --
NOT page ~34-35 as initially guessed, see Eq. 6.1.3.1-4) is the same thing
as PA/amplifier inefficiency. It is not, and there are actually THREE
distinct "efficiency" concepts worth keeping straight:
1. **PA/HPA drain efficiency** (our `pa_efficiency`) -- fraction of DC
   electrical power that becomes RF power inside the amplifier; the rest
   is wasted as heat in the amplifier circuitry. This is what
   `pa_efficiency` models: `DC_draw = P_transmit / eta`.
2. **Antenna aperture efficiency** (3GPP's 0.55-0.70 figure) -- a
   geometric/illumination-taper effect: how much of a dish's raw physical
   size becomes directive GAIN. Nothing here becomes heat -- untaken power
   just spreads into sidelobes instead of the main beam. Affects
   `sat_gain_dBi`-type figures, not power draw.
3. **Antenna radiation efficiency** (sometimes just "antenna efficiency")
   -- fraction of power delivered to the antenna terminals that is
   actually radiated vs. dissipated as ohmic/dielectric heat IN the
   antenna structure itself. This is the concept the user was actually
   asking about ("power our antenna loses while radiating") and it is
   real, but distinct from both 1 and 2 above.

Checked Ha et al. directly (the source of our 0.60 value,
src/energy_efficiency/Energy-Efficient_Precoding_and_Feeder-Link-Beam_
Matching_Design_for_Bent-Pipe_SATCOM_Systems.pdf, extracted to
outputs/ha_extracted_text.txt) to see which of these their "60% for both
antenna and HPA efficiency" comment actually means. Found: Ha et al. uses
TWO SEPARATE symbols -- rho_Sa/rho_GWA, explicitly named "the power
amplifier efficiency at the satellite" and used in exactly the same
`P_PA = (1/rho)(P_transmit - P_bb)` form as our `pa_efficiency`; AND a
separate, only-mentioned-in-prose "antenna efficiency," which (based on
where antenna gains G_GWA/G_Sa-Rx actually appear in their model -- only in
the channel/propagation equation, Eq. 1, never in the power-consumption
equations) most likely feeds into how THEY compute their fixed antenna
gain numbers, analogous to our `sat_gain_dBi`, not a second DC-power
divisor. Both factors happen to be set to the same 60% in their numerical
example, which is almost certainly why the code comment compressed them
into one description ("both... 60%") when only one (HPA efficiency) was
actually carried over into this codebase's `pa_efficiency`.

**Net conclusion**: `pa_efficiency=0.60` correctly models PA/HPA drain
efficiency ONLY (matches Ha et al.'s rho, and the PPA paper's eta_PA,
structurally). **Antenna radiation efficiency is not modeled anywhere in
this project's config.py at all** -- `sat_gain_dBi=20` (already flagged as
unverified via the 3GPP cross-check above) is a flat, independent number,
implicitly assuming a perfectly lossless antenna. If Ha et al.'s own
antenna-efficiency factor (whatever it actually multiplies in their gain
calculation) should also be reducing our effective `sat_gain_dBi`, that's
a second, so-far-unexamined possible source of over-optimism in the
current EE numbers, separate from and additional to the pa_efficiency
sensitivity question above. Not yet investigated further -- would need to
find exactly how Ha et al. derives their G_GWA/G_Sa-Rx numeric values in
Table I (not included in what was extracted so far) to know whether their
"antenna efficiency" is multiplicative on gain (dBi domain, i.e.
G_dBi_effective = G_dBi_ideal + 10*log10(0.6)) or something else.

**Finding, checked across 6 realizations (0, 2, 5, 10, 17, 21) -- genuinely
realization-dependent, not a fluke either way:**
- **Realizations 5, 17, 21** ("same strategy" case): EE's beam peaks land at
  essentially the SAME angles as the regular checkpoint's peaks (and MMSE's,

  in the same realizations).
- Working hypothesis: when all three users have comparable channel quality,
  EE matches the regular/MMSE spatial strategy just more efficiently shaped;
  when one user's channel is notably worse, EE seems to sacrifice serving
  that user rather than spend power on a low marginal-rate return -- makes
  sense given the Dinkelbach reward directly optimizes rate-per-power.

**Sum-rate statistics across all 30 realizations** (all at CSIT

| model | avg sum rate | beats MMSE how often | wins outright how often |
|---|---|---|---|
| MMSE (reference) | 2.037 | -- | -- |
| aod=0.0 | 2.247 | 22/30 | 9/30 |
| aod=0.025 (tuned-LR) | **2.493** (highest avg) | 19/30 | 7/30 |

Note the apparent contradiction resolves once you look at individual

highest AVERAGE -- aod=0.05's wins tend to be landslides, its losses also

**Three realizations examined in detail, illustrating WHY**:
- **Realization 0** (plotted, beampattern_across_error_models_
  realization0.pdf): sum rate aod0.0=2.14, aod0.025=2.92 (best here),
  aod0.05=2.77, MMSE=1.82 -- all three EE checkpoints beat MMSE. aod=0.05's
  beam concentrates almost entirely on User 1 (large_scale_fading=0.74,
  actually the WEAKEST of the three users here) with a sharp ~1130-gain
  spike, barely touching Users 2/3; aod=0.025 spreads more evenly across
  all three (moderate peaks near Users 1/2, smaller peak near User 3) and
  wins outright despite (or because of) that broader spread.
- **Realization 9** (beampattern_across_error_models_realization9.pdf) --
  the clearest "abandoning a user pays off big" case: sum rate aod0.0=0.58,
  aod0.025=1.63, **aod0.05=4.09** (landslide win), MMSE=0.20. aod=0.05's
  beam lands two SHARP, well-aligned peaks exactly on Users 2 and 3,
  completely skipping User 1. aod=0.0 and aod=0.025 both instead try to
  serve User 1 (with peaks OFFSET from its true angle, not well-aligned)
  and largely miss User 2 -- an imperfect attempt to serve a hard user
  that costs far more than it's worth, exactly the scenario aod=0.05's
  training presumably prepared it to recognize and avoid.
- **Realization 13** (beampattern_across_error_models_realization13.pdf) --
  the mirror case, "spreading power to serve everyone pays off": sum rate
  **aod0.0=4.69** (wins here), aod0.025=4.34, aod0.05=3.80, MMSE=4.64 (all
  close to MMSE -- a good channel realization for everyone). All three
  models' beams actually land on all three user angles reasonably well,
  but aod=0.05 clearly deprioritizes the middle user (near-zero gain
  there) in favor of taller peaks at the other two -- in THIS realization,
  where the "abandoned" user's channel was actually fine, that
  deprioritization costs it the lead rather than winning it.

**MMSE added to all three plots (user-prompted follow-up, job 152492,
cheap replot -- generate_mmse=True the whole time, just wasn't plotted
before)**. MMSE (gold) visually attempts to serve ALL THREE users in
EVERY one of these three realizations -- it has no CSIT-error-robustness
training, so it never learns to deliberately abandon a user the way the
EE checkpoints do. This makes MMSE's own sum rate swing wildly across the
three realizations (1.82 -> 0.20 -> 4.64) purely as a function of how
badly the CSIT error happens to hurt it in each specific draw, regardless
of user geometry: realization 9 is the starkest illustration -- MMSE's
beam looks spatially reasonable (three plausible peaks near all three
users) yet its sum rate craters to 0.20, WORSE than aod=0.0 (0.58) and
aod=0.025 (1.63) despite both of those also botching User 1, and far
worse than aod=0.05's 4.09 from deliberately not even trying to serve
User 1. Trying to serve everyone is not inherently safer under CSIT
error -- MMSE's naive completeness loses badly here to a policy that
learned when to give up on a user.

**Working conclusion**: the training CSIT error bound teaches the policy
HOW READILY to abandon a user, not just how gracefully to degrade.
Higher-error training (aod=0.05) learns a more aggressive
"concentrate-on-fewer-users" reflex that wins big when a user's channel
genuinely doesn't justify the power, and loses ground when it
misjudges a still-servable user as not worth serving. aod=0.025 (the
newly-adopted tuned-LR checkpoint) sits in between and comes out best on
average, though not most-often-outright-best -- consistent with it being
a genuine middle ground rather than simply "better."

## Background: what's already fixed (brief -- full derivations in git history of this file if needed)

1. **Raw-power reward dead-zone bug (FIXED)**: the Dinkelbach reward's
   power PENALTY term used to collapse to a constant whenever the raw
   (pre-clip) network output exceeded budget -- virtually always at
   error=0.5. A constant contributes zero gradient. Fixed in EE_sac.py: the
   power term now uses raw_power_precoder unconditionally; the rate term
   still correctly uses the physically-valid clipped precoder. New
   training_name suffix `_rawpow`. Necessary but not sufficient on its own
   -- the error-bound fix (above) was the dominant factor.
2. **action_bound_mode='tanh' (tried, deliberately abandoned)**: SAC's tanh
   log-prob correction biases against ever reaching near-saturated actions,
   inherent to any squashing-based actor bound.
3. **Entropy mechanism mismatch (found, tested, ambiguous)**: the paper
   uses a FIXED entropy scale (never updated) vs. this codebase's adaptive
   entropy tuning. Tested at error=0.5 only (now known-bad regime, job
   147503) -- performed worse than adaptive; never retested at low error.
4. **Entropy floor / network capacity (jobs 147485/147486)**: neither
   change broke the old ~1.82 ceiling at error=0.5 -- superseded, the
   ceiling was about training error scale, not entropy or capacity.
5. **Distance-scenario bug (FIXED)**: tx_power_distribution.py's
   `run_monte_carlo` used to hardcode a fixed 25km user distance (zero
   variance) instead of config.py's paper-matching 100km-mean/+-50km-roam
   default -- silently gave wrong power numbers (34%/64% instead of
   56%/56.5%). Fixed via `distance_value=None` (skip override, inherit
   config default), applied to the error=0.0/0.05 block specifically.
   **power_savings_N8K2_repro.pdf and the script's other, older blocks
   (2-model comparison, lambda sweep) still use the old wrong 25km value**
   -- don't trust those numbers without applying the same fix first.

## Process notes (still relevant)

- **sbatch only, always, no exceptions.** This interactive shell sits
  directly on a live shared compute node (fuchu) outside SLURM's
  accounting. Wrap any real compute in a .slurm script and submit via
  `sbatch`.

  matplotlib.use('Agg') + cfg.show_plots=False, re-asserted after
  constructing Config()/PlotConfig(). Also watch for bare plt.show() in any
  pre-existing script being reused -- same hang risk.

  `cfg.power_constraint_watt`, or the override silently won't propagate.

  occasionally race on log rotation, producing a "Logging error" +
  FileNotFoundError in .err -- doesn't affect training.
- SLURM job logs land at the REPO ROOT, not next to the .slurm scripts.

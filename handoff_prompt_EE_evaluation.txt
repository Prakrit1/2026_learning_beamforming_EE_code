## Triplet evaluation pipeline (NEW, 2026-08-05, committed b5e3253/fa5d7d2/c51a4b5)

Three new script+slurm pairs in `src/energy_efficiency/`, all pushed to
`origin/energy-efficiency-standalone`:

- **`rate_power_triplet.py` / `.slurm`**: Monte Carlo rate+power sweep
  (0-0.10 error, 11 pts, 10k MC) for all three checkpoints (clip-only
  precoder, matching how these Dinkelbach-rawpow checkpoints are always
  evaluated), a shared full-budget MMSE curve (system is identical across
  all three, so MMSE only run once), and a per-checkpoint matched-power
  MMSE curve (MMSE rescaled to that checkpoint's own measured power at
  each error level -- the fair "does SAC's beamforming itself compete"
  comparison this project has used since 2026-07-28). Saves
  `outputs/metrics/EE_lwin5000_3gpp_triplet/rate_power_triplet.gzip`.
- **`my_plotting_triplet.py` / `.slurm`**: reads that gzip, produces
  `error_sweep_triplet_matched_power_sumrate.pdf` (compact-legend single
  figure, the "parajuli.pdf" replacement) and `rate_power_triplet.pdf`
  (3-panel: rate/error, power/error, rate-vs-power trajectory).
- **`beampattern_triplet.py` / `.slurm`**: extends the earlier
  `beampattern_3gpp_nadir_aod0.py` pattern (one `generate_beampatterns()`
  call, shared channel realizations) to all three checkpoints + full-power
  MMSE. CSIT error=0.05 (matching every other beampattern script in this
  repo), 30 realizations, plots realization 0 by default (`--realization N`
  to pick another, `--plot-only` to replot an existing gzip without
  regenerating). Produces `beampattern_triplet_realization0.pdf` and
  prints beamwidth/coverage/offset stats to stdout (not yet pulled off the
  cluster into a local gzip as of this writing -- `EE_beampattern_3gpp_
  triplet_stats.gzip` exists on the cluster, check the job's `.out` for
  the printed table if the stats are needed before pulling it).

Run order: `rate_power_triplet.slurm` -> (afterok) `my_plotting_triplet.slurm`;
`beampattern_triplet.slurm` is independent of the other two.

### Results read off the figures (approximate -- read visually from the
PDFs, not from the raw gzip, which has not been pulled off the cluster
yet; pull `outputs/metrics/EE_lwin5000_3gpp_triplet/rate_power_triplet.gzip`
if exact numbers are needed)

- **Rate vs. error**: full-budget MMSE starts highest (~12.2 bps/Hz @
  error=0) and drops fastest, crossing below all three SAC curves by
  error~0.03-0.04. Among the three SAC curves, the established
  higher-training-error-degrades-more-gracefully pattern holds again:
  aod=0.05 (flattest, ~6.6->4.3 bps/Hz) ends highest at error=0.10;
  aod=0.0 (steepest, ~9.0->2.7 bps/Hz) ends lowest; aod=0.025 sits between
  them (~8.2->3.6 bps/Hz) and actually ends up close to aod=0.05 at high
  error despite starting closer to aod=0.0 -- worth a closer look with
  exact numbers if this curve shape matters for the paper.
- **Matched-power MMSE**: each SAC curve's matched-power MMSE dashed
  counterpart tracks close to it at low error and falls faster, so SAC
  overtakes its own matched-power MMSE somewhere in the low/mid error
  range for all three checkpoints -- consistent with every prior
  matched-power finding in this project (SAC's advantage is a robustness
  story, not a low-error-optimality one).
- **Power**: aod=0.0 draws ~46-47% of the 75W budget at error=0, drifting
  down to ~38% by error=0.10; aod=0.025 ~50-51% -> ~47%; aod=0.05 flattest
  at ~53-54% across the whole range. Matches the ~53-54% figure from the
  original single-checkpoint 2026-07-28 evaluation almost exactly, a good
  consistency check.
- **Beampattern (realization 0)**: all three SAC checkpoints aim
  reasonably well at the first two users (~1.47 rad, ~1.60 rad -- peaks
  close to the dotted true-angle lines). The THIRD user (~1.655 rad) looks
  underserved by all three: aod=0.0/0.025 show only a tiny residual bump
  near the true angle, and aod=0.05's nearby peak is visibly offset
  (~1.78 rad, well past the true angle). **This is one realization, not
  a general finding** (realization indices/severity vary a lot across a
  30-realization set, per this project's established beampattern
  conventions) -- but it echoes the earlier "EE_baseline drops a user"
  pattern found in the pre-cleanup fairness investigation. Worth checking
  the coverage-ratio stats (printed to the `beampattern_triplet` job's
  `.out`, or in `EE_beampattern_3gpp_triplet_stats.gzip` on the cluster)
  before concluding anything; not yet done.

## What's already fixed (condensed; full derivations in git history if needed)

1. Raw-power reward dead-zone bug: power penalty used to collapse to a
   constant when raw (pre-clip) network output exceeded budget. Fixed --
   power term now uses raw_power_precoder unconditionally (`_rawpow` suffix).
2. Training error bound (the dominant fix): was `EE_TRAIN_ERROR_BOUND=0.5`
   everywhere (10x the reference paper's own range); now trained at
   paper-matching 0.0/0.025/0.05.
3. Distance-scenario bug: `tx_power_distribution.py` used to hardcode 25km
   user distance instead of the paper-matching 100km-mean/+-50km-roam.
4. 3GPP TR 38.821 alignment (2026-07-27): `sat_gain_dBi` 20->30,
   `power_constraint_watt` 100->75 (both env-overridable via
   `EE_SAT_GAIN_DBI`/`EE_POWER_BUDGET_WATT`), justified against TR 38.821
   Set-1 (LEO-600, S-band, 30 dBi, ~75W implied per-beam EIRP). **Any
   evaluation of checkpoints trained before 2026-07-27 needs those two env
   vars set to the OLD values (20/100) or the numbers are silently wrong.**
   `circuit_power_watt=1.0/element` and `pa_efficiency=0.60` were checked
   and deliberately kept as-is (bracketing arguments, not exact matches --
   see git history if the full justification is needed).

## Abandoned lines (tried 2026-07-29 through 2026-08-03, deleted from disk 2026-08-04)

Deterministic-lambda estimation ("detlam"), EMA-smoothing + warm-start on
top of it, target-entropy annealing, and the power-conditioned reward mode
were all implemented, piloted, and fully evaluated against matched-power
MMSE -- none closed the gap (stayed in the 43-66% range throughout,
sometimes WORSE than the plain `lwin5000` mechanism they were meant to
fix). `EE_sac.py`/`soft_actor_critic.py` were reverted to plain `lwin5000`
on 2026-08-03. Separately, a Jain's-fairness reward term (weight sweep
0.5/1.5/3.0) showed a real effect (weight=1.5 was the best rate/fairness
tradeoff, and fairness weighting visibly fixed a "dropped user" failure
mode in beampattern analysis) but was also deleted in the 2026-08-04
cleanup as out-of-scope for the current working line; worth revisiting if
the triplet's realization-0 beampattern concern (see above) turns out to
be a real pattern rather than a one-off. The elev30 geometry was dropped
for a structural dropped-middle-user problem (tight angular spread ->
highly correlated channels) that would need fairness weighting to fix
properly -- not attempted. All reasoning, numbers, and job IDs for these
abandoned lines are preserved in this file's git history (search commits
before `b37061a`, "Remove scripts/slurms tied to abandoned ... lines") if
ever needed again -- not reproduced here.

## Process notes (still relevant)

- matplotlib gotcha: `PlotConfig()` resets `text.usetex` to `True` on
  construction; always `matplotlib.use('Agg')` + `cfg.show_plots=False`,
  re-asserted after constructing `Config()`/`PlotConfig()`.
- SLURM job logs land at the REPO ROOT, not next to the `.slurm` scripts.
- CSIT error model perturbs `additive_error_on_cosine_of_aod`, NOT the AoD
  angle itself -- error bound `b` maps to roughly `b/sin(theta)` radians
  of real angular offset at our operating angles (~1.33-1.81 rad).
- Realization indices are only comparable WITHIN one gzip/job -- different
  beampattern scripts (or reruns of the same one) draw independent random
  realizations.
- The reference paper PDF is at `src/energy_efficiency/Model-Free_Robust_
  Beamforming_in_Satellite_Downlink_Using_Reinforcement_Learning.pdf`
  (Schroder et al., IEEE Open J. Comm. Soc. 2025). Fig. 3 (N=16/K=3,
  d_K=100km) is the scenario this whole investigation targets.
- `docs/EE_formulation.tex` (in THIS repo) and the `EE_precoder` Overleaf
  project are two SEPARATE documents -- don't confuse them. It's not yet
  decided whether `docs/EE_formulation.tex` will be merged into
  `EE_precoder` or kept as a separate internal derivation doc; ask the
